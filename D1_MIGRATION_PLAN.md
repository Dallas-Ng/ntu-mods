# D1 Migration Plan — NTU Mods data layer

Status: **design agreed, not started.** This document is the handoff spec.

## 1. Context

NTU Mods (Astro + React islands, deployed to Cloudflare Workers) currently stores
all module data as static JSON committed to git:

- `src/data/api/` — 139 files, **70 MB**, git-tracked
- `public/data/api/` — 138 files, **67 MB**, git-tracked, a near-duplicate produced
  by `scripts/build-static-data.mjs`

Data is produced by a Python scraper (`scraper/`) run manually on the maintainer's
machine, copied into `src/data/api/` by `scraper/stepfinal_upsync.py`, committed,
and shipped in a PR. There is no CI. A single KV namespace (`MODULE_DATA`,
id `98c8dfc5fcfb4dd180c30d37b4d000aa`) holds per-module slices used only by the
on-demand historic-snapshot route.

**Goal:** replace the JSON-file storage and the hand-written aggregation scripts
with a Cloudflare D1 database as the single source of truth, and restructure the
scraper pipeline to load D1 in scoped, idempotent, re-runnable units.

Explicitly **out of scope** for now: GitHub Actions / CI, cron automation, moving
the scraper itself onto Workers. The pipeline stays manually triggered. The design
must not *block* later automation.

## 3. Bugs and dead code found during design (fix or account for these)

1. **`index-map.json` is dead.** Generated by `stepfinal_upsync.py` (114k entries,
   5.8 MB), zero consumers anywhere in `src/`, `scripts/`, or components. Delete.

2. **`latest semester` has two disagreeing sources.** `src/lib/semesters.ts` takes
   `semesters.json[0]` — the *portal's* semester list from scraper step 1 — which is
   scraped independently of whether step 2 has loaded any courses for it. When NTU
   lists a new semester before it is scraped: `/mods` defaults to an empty semester,
   the timetable builder fetches an indexes file that 404s, and every module renders
   the "Not offered in the current semester" banner.

3. **The portal's semester ordering is not consistent.** Actual order in
   `semesters.json`: `2026;1  2025;2  2025;1  2025;S  2024;1  2024;2  2024;S  2023;2`.
   AY2025 lists as `2,1,S`; AY2024 lists as `1,2,S`. Chronologically it is
   Sem 1 (Aug–Nov) → Sem 2 (Jan–Apr) → Special Term (May–Jun). List position is not
   a reliable ordering signal.

4. **`main.py --from` silently skips semesters.** It does
   `cutoff = semesters.index(from_semester); semesters[:cutoff+1]`, assuming reliable
   newest-first ordering. Given (3), `--from "2025;1"` yields
   `2026;1, 2025;2, 2025;1` and drops `2025;S`, which is chronologically newer.
   This is a live bug independent of the D1 work.

5. **`step3_convert_mdata.py` is silently first-programme-wins.** `if code not in result:`
   means when the same course appears under multiple programme codes with differing
   title/credits/fields, all but the first are discarded with no warning.

6. **Titles and descriptions vary across semesters** — 700 title changes, 1,522
   description changes across the 45 semesters. Module fields are genuinely
   offering-scoped. A single global `modules` table would corrupt historic snapshots.

7. **30% of prerequisites are free text**, e.g.
   `[["NGL students are taking AL1001, cannot read AB1088"]]`.
   `scripts/build-static-data.mjs` currently drops these via `MODULE_CODE_RE.test(item)`.
   The schema must retain raw text alongside the resolvable FK.

8. **Prerequisite AND/OR nesting looks wrong.** `AB0602` is
   `[["AB0601"],["CC0001"],["SP0001"],["AL1601"],["AB1600"]]`. Under `scraper/README.md`'s
   stated "outer = AND, inner = OR" rule that means 5 mandatory prerequisites, which is
   almost certainly not intended. Preserve group structure on load so this is fixable
   later without a rescrape; do not silently reinterpret it.

9. **`src/astro/pages/timetable/index.astro:47` hardcodes** `1,134 modules · 4,846 class indexes`.

10. **`README.md` §"Data Pipeline" is stale.** It documents
    `scripts/scrapers/1_academic_year.py … 5_exams.py` and
    `node scripts/transform-api-data.js` — none of which exist. The real pipeline is
    `scraper/step1..step5*.py` + `stepfinal_upsync.py`.

## 4. Target schema

Design rule applied throughout:

> **Derive at load** when every input is inside one semester
> (`faculty`, `categories`, `start_min`, `end_min`, `prefix`, `level`).
> **Derive at read** when inputs span semesters (`is_current`, `latest_sem`) —
> loading one semester silently falsifies a stored cross-semester value for every
> other row.

```sql
CREATE TABLE semesters (
  sem       TEXT PRIMARY KEY,   -- "2025_2"
  code      TEXT NOT NULL,      -- "2025;2" (NTU portal form)
  year      TEXT NOT NULL,
  semester  TEXT NOT NULL,      -- 1 | 2 | S | T
  name      TEXT NOT NULL,      -- "Acad Yr 2025 Semester 2"
  sort_key  INTEGER NOT NULL    -- int(year)*10 + {1:1, 2:2, S:3, T:4}
);

-- Per-semester module record. Title/description live here because they vary
-- across semesters (see finding 6). faculty/categories are computed at load
-- from this offering's own programmes — intra-semester derivation, safe.
CREATE TABLE offerings (
  code TEXT NOT NULL,
  sem  TEXT NOT NULL REFERENCES semesters(sem),
  title TEXT NOT NULL,
  au    TEXT NOT NULL,
  faculty    TEXT,              -- precomputed (replaces client-side get-module-faculty.ts)
  categories TEXT,              -- precomputed JSON array (replaces get-module-category.ts)
  description TEXT,
  grade_type  TEXT,
  not_available_to_programme          TEXT,
  not_available_to_all_programme_with TEXT,
  not_available_as_bdeue_to_programme TEXT,
  not_available_as_core_to_programme  TEXT,
  not_available_as_pe_to_programme    TEXT,
  not_offered_as_bde TEXT,
  not_offered_as_ue  TEXT,
  mutually_exclusive_with TEXT, -- JSON array
  extras TEXT,                  -- JSON object; scraper catch-all, no migration on new NTU fields
  PRIMARY KEY (code, sem)
);

CREATE TABLE programmes (
  id      INTEGER PRIMARY KEY,
  key     TEXT NOT NULL UNIQUE, -- "CSC;;1;F"
  faculty TEXT,
  is_core INTEGER               -- the 4-segment heuristic from get-module-category.ts
);

CREATE TABLE offering_programmes (
  code TEXT NOT NULL,
  sem  TEXT NOT NULL,
  programme_id INTEGER NOT NULL REFERENCES programmes(id),
  PRIMARY KEY (code, sem, programme_id)
);

CREATE TABLE class_indexes (
  code TEXT NOT NULL, sem TEXT NOT NULL, index_key TEXT NOT NULL,
  PRIMARY KEY (code, sem, index_key)
);

CREATE TABLE class_slots (
  code TEXT NOT NULL, sem TEXT NOT NULL, index_key TEXT NOT NULL,
  slot_no INTEGER NOT NULL,
  type TEXT, grp TEXT, day INTEGER,
  time TEXT,                        -- "0830-0930", kept for display
  start_min INTEGER, end_min INTEGER, -- precomputed; kills client parseInt(time.split("-"))
  venue TEXT, remarks TEXT, duration INTEGER,
  PRIMARY KEY (code, sem, index_key, slot_no)
);

CREATE TABLE exams (
  code TEXT NOT NULL, sem TEXT NOT NULL,
  date TEXT, day INTEGER, start_time TEXT, end_time TEXT,
  name TEXT, duration INTEGER,
  PRIMARY KEY (code, sem)
);

-- raw_text ALWAYS populated; requires_code only when the item parses as a module code
CREATE TABLE prerequisites (
  code TEXT NOT NULL, sem TEXT NOT NULL,
  group_no INTEGER NOT NULL,   -- AND-group
  item_no  INTEGER NOT NULL,   -- OR-item within group
  requires_code TEXT,
  raw_text TEXT NOT NULL,
  PRIMARY KEY (code, sem, group_no, item_no)
);

-- Load ledger: observability + no-op detection + the row-count safety guard
CREATE TABLE loads (
  sem   TEXT NOT NULL,
  scope TEXT NOT NULL,          -- 'courses' | 'exams'
  loaded_at   TEXT NOT NULL,
  source_hash TEXT,             -- hash of the raw scrape output
  row_counts  TEXT,             -- JSON, per table
  PRIMARY KEY (sem, scope)
);

CREATE INDEX idx_offerings_sem     ON offerings(sem);
CREATE INDEX idx_offerings_code    ON offerings(code);
CREATE INDEX idx_slots_sem         ON class_slots(sem);
CREATE INDEX idx_slots_code_sem    ON class_slots(code, sem);
CREATE INDEX idx_prereq_requires   ON prerequisites(requires_code);
CREATE INDEX idx_offprog_programme ON offering_programmes(programme_id);
CREATE INDEX idx_semesters_sortkey ON semesters(sort_key);
```

**No `modules` table, no `is_current` column, no `latest_sem` column.**

### Latest semester — one shared definition

"Latest" means *the newest semester that actually has data*, ordered by `sort_key`
(derived from the semester code), never by insertion order or list position:

```sql
SELECT sem, year, semester, name
FROM semesters
WHERE EXISTS (SELECT 1 FROM offerings o WHERE o.sem = semesters.sem)
ORDER BY sort_key DESC
LIMIT 1;
```

Three consumers need this (build-time constant generation, the snapshot route's
`isCurrentOffering`, the exams page). Keep it as **one shared SQL constant in code**
— a `.sql` file or a TS module — not copy-pasted three times, and not a database
view. (Views were considered and rejected: in SQLite a view is pure query
substitution with no storage or performance effect, so it buys only deduplication,
which a shared constant already provides with less ceremony and better repo
visibility.)

The module-summary rollup that replaces `modules.json` / `module-map.json` is a
plain query at its single call site (the build step), not a view:

```sql
WITH ranked AS (
  SELECT o.code, o.sem, o.title, o.au, o.faculty, o.categories,
         ROW_NUMBER() OVER (PARTITION BY o.code ORDER BY s.sort_key DESC) AS rn
  FROM offerings o JOIN semesters s ON s.sem = o.sem
)
SELECT code,
       substr(code, 1, 2)                  AS prefix,
       CAST(substr(code, 3, 1) AS INTEGER) AS level,
       title, au, faculty, categories,
       sem AS latest_sem,
       CASE WHEN sem = :latest_sem THEN 1 ELSE 0 END AS is_current
FROM ranked WHERE rn = 1;
```

The `semesters` catalogue is the one table where **upsert is correct** — it is
append-only reference data; NTU does not un-publish past semesters.

## 5. Pipeline redesign

### Scope model

The unit of work is **(semester, scope)**. Two scopes per semester, because they
have independent sources and triggers:

| Scope | Source | Writes |
| --- | --- | --- |
| `courses` | portal scrape (step 2 + 2b) | offerings, offering_programmes, class_indexes, class_slots, prerequisites |
| `exams` | exam CSV, downloaded manually | exams |

Re-running `courses` must not delete `exams`.

### Replace, not merge

A load is `DELETE WHERE sem = ? (within scope)` then `INSERT`, in one transaction.

**Do not build merge/upsert semantics for scoped data.** Upsert cannot express
deletion: if NTU cancels index `10001`, an upsert leaves the row in place and
students see a phantom class forever. Replace also preserves the property that
`2025_2` in the database is exactly what NTU published at scrape time — with merge,
the table becomes a sediment of every scrape ever run and no re-run can restore it
to a known state.

Two places merge *is* correct: the `semesters` catalogue (above), and the
multi-programme duplicate — which in this schema dissolves by normalization
(`offering_programmes` is a proper many-to-many) rather than needing merge logic at
all. That deletes the `searchKeys` aggregation in `step3_convert_mdata.py`.

### Conflicts: detect and log, do not auto-resolve

Keep explicit precedence rules where two sources describe the same field —
`step3_convert_mdata.py` already has one ("content portal is authoritative for
restriction fields"), and that pattern should survive. Log cross-programme
conflicts (finding 5) rather than silently taking the first. A generic "try to
merge" makes real upstream changes indistinguishable from merge artifacts.

### Safety guard (required before any future automation)

Replace semantics + automation is dangerous: if the portal returns an error page or
a session expires, the scraper yields zero courses and a blind replace wipes the
semester. **Before committing a load, compare against `loads.row_counts` and refuse
if the count drops more than ~20% without an explicit `--force`.**

### Target CLI

```bash
pipeline discover                                          # refresh semesters catalogue only
pipeline load --scope courses --sem "2025;2"
pipeline load --scope courses --sem all --from "2025;1"
pipeline load --scope courses --sem all --rebuild
pipeline load --scope exams   --sem "2025;2" --csv ./exams-2025-2026-s2.csv
```

Step 1 stops being a pipeline stage and becomes `discover`. Steps 2/2b are unchanged
(raw scraping). Steps 3/4/5 and `stepfinal_upsync.py` are replaced by a single
normalising loader that reads `02_courses_*.json` + `02b_content_*.json` + exam CSV
and writes schema rows directly.

`sort_key` must be computed from the semester code, never from list position:

```python
SEM_ORDER = {"1": 1, "2": 2, "S": 3, "T": 4}   # S/T run after Sem 2 of the same AY
sort_key = int(year) * 10 + SEM_ORDER[semester]
```

## 6. Read path — how the app gets data

### Build time (Node, no Worker binding) — the important design decision

`/mods/[module]` prerenders **4,317 pages**, and each currently does a 45-file scan
(`getModuleCurrentSemester`, `getModuleSemesters`) plus a 1.2 MB whole-file parse
(`getAllModuleMetadata`) just to read one module.

Do **not** proxy 4,317 pages' queries over HTTP. Instead: **one SQLite file, two
runtimes.** The build downloads the database once (`wrangler d1 export`) and queries
it locally via `node:sqlite`; the runtime Worker queries the same schema through the
D1 binding. Identical SQL both sides, zero network per page. This makes the build
faster than today.

(`better-sqlite3` is the boring alternative if the `node:sqlite` experimental
warning is unwelcome.)

### Client — stays bulk, but generated from SQL

The timetable generation algorithm and day/time filtering genuinely need the whole
semester index set in-browser. Keep `modules.json`, `indexes/{sem}.json` and
`random-samples.json` as **static assets** (requests to static assets are free and
unlimited on Workers) — but generate them from D1 queries at build instead of the
hand-rolled JS aggregation in `build-static-data.mjs`.

Consequence to accept: **D1 is the source of truth; the build is the publication
step.** Loading a semester into D1 does not change the live site until a rebuild.
Only the on-demand `/mods/:code/:year/:semester` route reflects D1 immediately. This
is the same coupling as today (data in git → rebuild → deploy), so not a regression
— but "decouple data updates from redeploys" is *not* a benefit this migration
delivers.

### Mapping

| Today | D1 |
| --- | --- |
| `getModuleCurrentSemester` — 45-file scan | `SELECT sem FROM offerings WHERE code=? ORDER BY sort_key DESC LIMIT 1` |
| `getModuleSemesters` — 45-file scan | same, no LIMIT |
| `getAllModuleMetadata` — 1.2 MB parse to read 1 module | `SELECT … WHERE code=? AND sem=?` |
| `RelatedModules` — whole-file parse + prefix filter | `WHERE prefix=? AND code<>? LIMIT 9` |
| `getPrerequisiteGraph()` | two queries, or `WITH RECURSIVE` |
| `getModuleSnapshot` — KV + ASSETS + self-heal | one joined query; **delete the self-heal logic and the KV namespace** |
| `module-map.json` | `SELECT code FROM offerings GROUP BY code` |
| `index-map.json` | **delete — dead code** |
| `prerequisite-graph.json` | query |
| exams page fallback loop (`exams/index.astro:19-35`) | `WHERE EXISTS (SELECT 1 FROM exams …) ORDER BY sort_key DESC LIMIT 1` |
| `modules.json`, `indexes/*.json`, `random-samples.json` | still static artifacts, generated by SQL at build |

## 8. Migration order

1. Write schema + `wrangler d1 create ntu-mods`.
2. Write the loader; load all 45 semesters **from the existing `src/data/api` JSON** —
   no rescrape needed, it is the same data.
3. **Verify parity before deleting anything.** Query D1 and diff against the current
   JSON for a sample of modules/semesters across several years.
4. Add the build-time `node:sqlite` reader; rewrite the six `src/lib/server/get-*.ts`
   behind their existing signatures. Pages unchanged at this step.
5. Rewrite `getModuleSnapshot` to use the D1 binding; drop KV.
6. Regenerate the client artifacts from SQL in `build-static-data.mjs`. Client hooks
   keep the same URLs, so no client changes in this step.
7. Only then: drop `searchKeys` from the client payload and switch `filter-modules.ts`
   to the precomputed `faculty` / `categories` columns.
8. Delete the JSON trees, update `.gitignore`, fix the stale README §Data Pipeline.
9. Rewrite the scraper's transform half against the new schema + scope model.

## 9. Verify early — RESOLVED

Measured against a real dev database, `ntu-mods-dev`
(`08aaa8e2-45a6-4598-b74d-3a7194bf1f36`, APAC/SIN). Production is untouched.

**D1 transaction size — resolved, no chunking needed.**
`wrangler d1 execute --remote --file` is **atomic across the entire file**. The
whole 790k-row corpus loaded as one transaction: 1,823 statements, 784,922 row
changes, 33.6 s of SQL time. Verified by deliberately appending a bad statement
to a scoped load — the file's `DELETE`s and a sentinel `INSERT` both rolled back,
leaving the semester exactly as it was. Per-semester atomicity is therefore free.
The largest single semester (`2023_1`: 1,147 offerings / 7,797 indexes / 20,322
slots) loads in 117 statements and 1.2 s.

Three hard D1 limits found while getting there:

| Limit | Value | Consequence |
| --- | --- | --- |
| Max SQL statement length | ~100 KB | Batch INSERT rows by **bytes**, not row count. A fixed 500-row batch of `offerings` (each with a full description) hit `statement too long: SQLITE_TOOBIG`. `scripts/db/load-semester.mjs` targets 90 KB. |
| Compound `SELECT` terms | fewer than 10 | A 10-term `UNION ALL` count query fails with `too many terms in compound SELECT [code: 7500]`. Use scalar subqueries. |
| Import polling | flaky | One scoped load failed with `Not currently importing anything` and succeeded on retry. Loads are idempotent (replace, not append), so blind retry is safe — but the pipeline must retry rather than treat it as a data error. |

**Plan tier — confirmed Paid, empirically.** The full load reported
`rows_written: 3,023,108` (index writes included) in a single operation and was
not throttled; the free tier caps at 100k written rows/day. Note that figure:
a full rebuild costs ~3M billed writes, and even one semester costs ~230k, so
routine per-semester loads also exceed the free daily allowance. Resulting
database size: **108.9 MB**, against a 10 GB per-database limit.

**Prerequisite AND/OR semantics — decided: store verbatim, interpret never.**
`prerequisites` keeps `group_no` / `item_no` exactly as scraped and always
populates `raw_text`. The loader bakes in no interpretation, so finding 8 stays
fixable in the read layer without a rescrape.

### Additional finding (11): every module is tagged CORE

All 744 distinct `searchKeys` in the corpus have exactly 4 semicolon-separated
segments, but `src/lib/get-module-category.ts` tests for exactly that to decide
`CORE`. So every offering with at least one `searchKey` — which is all of them —
is tagged `CORE`, and the CORE filter is a no-op.

Segment 2 is the study year (`1`–`5`) for a real programme core listing and `X`
for the `GLOAD` / `MLOAD` / `GERP` / `USP` / `CNY` / `EP` buckets, so the intended
test was almost certainly "segment 2 is a digit". `programmes.is_core` stores that
correct definition. `offerings.categories` deliberately reproduces the *current*
buggy behaviour so the migration is provably behaviour-preserving; fixing it is a
separate, visible commit.

Confirmed by measurement after the migration: the CORE filter matches
**4,317 of 4,317** modules. For comparison, GLOAD matches 3,131, MLOAD 1,766,
GERP 237 and CNY 98.

A second, smaller bug in the same function: `USP` is mapped to `CNY`, so the
`USP` bucket (6 programme keys) is indistinguishable from Chinese New Year
modules. `TYPE_PRIORITY` in `filter-modules.ts` still lists `USP`, which
therefore can never match.

## 8a. Deviation in step 9: steps 3/4/5 were kept

The plan said steps 3/4/5 and `stepfinal_upsync.py` would all be replaced by "a
single normalising loader". In practice only the aggregation half was replaced.

Steps 3/4/5 stay as the normalisers. They carry a lot of hard-won parsing —
`smart_title`, `_clean_description`, the inline-list and dash-list splitters, the
label→field map, `parse_prerequisite`, the compound `LEC/STUDIO` type
normalisation, and the "content portal is authoritative for restriction fields"
precedence rule. Porting that to JavaScript would risk silent behaviour drift
across 28,628 offerings for no benefit, since their output shape is already the
loader's input shape.

What *was* replaced is the hand-written data aggregation the plan actually
objected to: `stepfinal_upsync.build_derived_files`, which merged all 45
semesters into `module-map.json` and the dead `index-map.json`. Both files are
deleted; the equivalent queries live in `src/lib/server/db/queries.ts`.

`scripts/db/load-semester.mjs` shares its row construction with the bootstrap
loader through `scripts/db/rows.mjs`, so `yarn db:verify` proving the backfill
correct also covers the pipeline. `stepfinal_upsync.py` now only copies files
into `src/data/api`, and exists purely as the CI fallback described below.

## 9a. New blocker found during implementation: the build cannot reach D1

Step 8 of the migration order ("delete the JSON trees") assumed the build can
obtain the database. It cannot yet.

`yarn build` reads `db/ntu-mods.sqlite`. Locally that comes from `yarn db:pull`
(`wrangler d1 export`). **Cloudflare Workers Builds has no wrangler credentials**,
so the same command fails there — and the SQLite file is 103 MB, far too large to
commit.

Until that is solved, `scripts/db/sync-db.mjs` rebuilds the database from the
JSON under `src/data/api` when the file is missing, which keeps CI green.
**That fallback is the only remaining reason `src/data/api` exists.** Options,
roughly in order of preference:

1. Put a scoped Cloudflare API token in the Workers Builds environment and run
   `yarn db:pull` in the build. Smallest change; the token needs D1 read only.
2. Publish the SQLite file to R2 on each load and fetch it over HTTPS at build
   time. No token needed if the bucket has a public route.
3. Keep the JSON as the build input permanently, treating D1 purely as the
   serving layer. Cheapest, but leaves the duplication this migration set out
   to remove.

`public/data/api` (67 MB) is already gone from git — it is regenerated from the
database on every `yarn dev` and `yarn build`.

## 10. Constraints

- Package manager is **yarn**, not npm/pnpm.
- Do not add `Co-Authored-By` trailers to commits.
- `wrangler.jsonc` at the repo root is deliberately assets-only; the adapter emits
  the real config at `dist/server/wrangler.json`. Deploy with
  `npx wrangler deploy --config dist/server/wrangler.json`. Read the comments in
  `wrangler.jsonc` before editing it — they document two non-obvious upstream
  workarounds.
- `wrangler d1 time-travel` gives 30-day point-in-time restore, which replaces
  "git history was the safety net for bad data" once the JSON leaves the repo.
